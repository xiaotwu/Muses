# R002 身份与多发行关系收口

日期：2026-09-19。范围：批次 22。没有执行远端账号写入，也没有修改用户当前资料库。

## 实现

- 新增 `CatalogTrackReleaseMembership`，以 Track UUID、稳定发行 ID、顺序、证据类型及来源 import/item ID 保存 Track–Release 多对多关系。重复来源条目分别保留，目录投影按 Track／发行去重并采用最小来源顺序。
- `Track.releaseCatalogID`／`releaseOrder` 只保留旧库兼容和确定性主发行；新关系不会以第二个发行覆盖既有稳定主身份。显示名称不参与持久身份或合并。
- YouTube Music 专辑导入、在线专辑／单曲导入和历史身份审阅共用关系写入边界。目录重建只读取关系及旧字段的内存兼容边，不在启动时暗中迁移。
- 身份预览允许同一 Track 的多个直接权威发行同时进入待应用关系；迁移收据版本 2 记录每条确切证据。应用、失败恢复和显式回滚只增删本次关系，并保留 UUID、收藏、播放次数、歌单、历史、笔记和书签。
- SwiftData schema 升至 generation 4。逐表审计排除新的迁移目标关系表，但继续覆盖所有既有用户数据表；启动不自动执行历史身份应用。

## 验收

- 双发行磁盘夹具：同一 Track UUID 同时投影到两个稳定 playlist 发行；相同标题的两个发行不合并，兼容主发行保持确定；回滚精确删除两条新增关系并恢复旧主身份。
- 导入与目录专项覆盖来源类型、source import/item ID、顺序、重复证据、同视频不同 UUID 隔离、既有稳定身份不覆盖及失败／中断恢复。
- 用户真实库先通过只读 SQLite online backup 复制到 `/tmp`。源库包含 506 Track、1 个普通 `PL...` 导入和 506 个条目，`quick_check=ok`；它没有可作为专辑发行的直接证据，因此预览正确产生零候选。
- 真实副本完成 generation 4 schema 升级及独立进程冷重开；升级前后既有逻辑用户表逐表数量和摘要一致，关系表为 0，Track 仍为 506。源库关系表仍不存在，主数据库 SHA-256 前后均为 `708a9bc57503e2e7dc26466bf4fb59dab7148b0731d107d57a18dbd97469c5d0`。
- `swift test --no-parallel`：602 tests／86 suites 通过。真实库副本的显式升级阶段和冷重开审计阶段分别通过。`swift build -c release` 通过；仅保留 3 条既有无关编译警告。

## 边界

真实库零候选不是把普通播放列表推断为专辑。带权威专辑证据的应用／回滚由包含重复条目、两发行及用户数据的磁盘夹具覆盖；后续 R009／R016 新增 renderer 或详情来源时，只有稳定 browse／playlist ID 和明确来源才能写入同一关系边界。
